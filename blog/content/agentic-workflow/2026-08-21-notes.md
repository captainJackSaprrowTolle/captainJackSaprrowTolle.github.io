## Module 1 - Task Decomposition / Identifying Building Blocks

### 吴教授的工作日常

> 我在构建智能体工作流时，很多工作就是审视个人或企业正在做的工作，然后尝试找出利用这些构建块，如何将它们按顺序组合在一起，以执行我希望系统执行的任务。

### Highlight：从人脑到电脑的思考

最重要的就是这个"人脑到电脑"的思考转换：

> 构建智能体工作流的核心技能之一，就是审视某人所做的大量工作，并识别出可以用以实现它的离散步骤。

### 如何拆解一个步骤

吴教授教你如何思考这个问题：

> 当我审视这些独立的离散步骤时，我一直在问自己的一个问题是：这个步骤能否通过 LLM 或我能调用的工具（如 API 或函数调用）来实现？
>
> 如果答案是否定的，我通常会再问自己：如果是人类，我会怎么做这一步？是否有可能将其进一步拆解，或分解为更小的步骤，从而使其更适合使用 LLM 或我们拥有的软件工具来实现？

### 迭代改进

英雄所见略同：

> 事实证明，在构建智能体工作流时，你通常会构建出一个初始的任务拆解和初始智能体工作流，然后你需要不断地迭代和改进多次，直到它达到你满意的性能水平。为了推进这个改进过程（这对许多项目来说都至关重要）……

## 看视频有感

1. 最早的 AI 就是 LLMs + tool calling 这种模式，那时候大家觉得这个不够智能，因为写脚本也能实现，不新奇。
2. 能有多强的能力拆分 building blocks，这种细分的能力很重要，否则就是一坨混沌。
3. 前一份工作里的人不允许迭代他们的 AI 工作流，甚至认为 AI 产出的不够完美就彻底否定这条路，所以他们不配拥有 AI。

### moudule 1 - Evaluating agentic AI(evals)

吴教授提出评估agentic workflow输出质量好坏的方法论，是从模型的输出着手，看看整体的输出质量，同时关注每个组件，我理解为步骤之间的输出质量
评估方法有LLM as judge ,就是把结果作为输入给到LLM来评估打分，另一个是写脚本，输出统计数据来看

理念上，我的工作里非常忽视Evaluating这个工作的重要度，甚至从来不会分析好坏。
当前的理解非常的肤浅，就是每天跟AI去battle来回多轮对话，直到找到正确的输出效果。
毫无疑问这个方式非常的耗费精力，使得AI黏在手上无法脱身去做其他事，每天就是盯着AI的输出。

吴教授提出的agentic workflow则完全是系统的视角来思考人的工作。单打独斗是不可持续的，而吴教授的方法是拥有巨大潜力的，值得学习！

以后要把claude code, codex当作一个source，我要做的是审视人的工作，拆解出可细分的buiding blocks, 然后evals迭代评估每个步骤，每个组建的输出，下一步是要提高Evaluating的效率，帮助每个步骤都有合理的评估。

## 老师评语

方向抓得很准：从"单打独斗回复 AI"转向"系统视角审视人的工作、拆出 building blocks、逐组件评估"，这正是吴教授这两节课的核心骨架，理解到位。

但有两处执行层面的认知偏差，值得注意：

**Gap 1：Evals 是自下而上"长出来"的，不是提前"设计好"的**

你写到"下一步是要提高 Evaluating 的效率，帮助每个步骤都有合理的评估"——这个提法隐含了一种倾向：想在动手之前就把每个步骤的评估指标提前规划齐全。吴教授的实际做法相反：构建智能体之前，你几乎不可能预判会出什么错。正确顺序是先搭原型 → 跑起来看输出 → 手动发现具体的意外错误（比如提到了竞争对手）→ 针对这一个具体错误才补写对应的 eval。评估体系是随着你对错误模式的认知逐步长出来的，不是一开始就追求"全量覆盖"。

**Gap 2：自动化评估之前，有一段"人工看 Trace"的阶段不能省**

你提到了 LLM as judge 和写脚本统计两种评估方法，但笔记里跳过了它们之前必经的一步：错误分析（Error Analysis）。自动化 eval 的前提是人类先去读模型中间步骤的轨迹（trace / 管道输出），肉眼诊断到底是哪个 building block 掉了链子。这段手动看 trace 的精力省不掉——只有先看懂错误长什么样，才谈得上把它提炼成一条高效的自动评估规则。

一句话总结：你已经想清楚了"要拆、要评"，接下来要补的是"怎么拆着评"——先跑、先看、先手动找错，评估规则是从具体错误里长出来的，不是先画蓝图。
